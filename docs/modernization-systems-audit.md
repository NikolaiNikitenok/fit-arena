## Подтвержденные риски

### P1: потеря награды при обрыве ответа

`server/clans.ts:claimRaid`, `claimWar` сначала выполняют `guard.claim`, затем возвращают payload. `claimGift` сначала меняет `member.gift`. `server/index.ts` отправляет `clanClaimed` после этой мутации. Монеты/предметы начисляет только `src/clan/ClanScreen.tsx` в useEffect после получения ответа через `useClan.ts`. Восстановления payload на reconnect нет; следующий claim возвращает «уже забрана». Клиентская дедупликация `progress.claimRaid/claimWar/claimClanGiftRange` защищает от повторного начисления, но не от потери ответа. Это не исправляется сменой баланса.

Воспроизведение на локальных тестовых данных: создать клан и законченный рейд с участием игрока как в `server/fairplay.test.ts`; вызвать `claimRaid` и намеренно отбросить ответ без изменения клиентского Progress; повторить вызов. Второй ответ — ошибка «уже забрана», а Progress остался без награды. Аналогично для войны/подарка. UI-сценарий: перехватить входящий WebSocket `clanClaimed`, разорвать сеть до доставки, переподключиться и проверить отсутствие возможности восстановить награду. Нужны durable receipts с безопасным повтором ответа и совместимым подтверждением применения; старые отметки не следует автоматически превращать в новые выплаты.

### P1: сервер не доказывает физическое выполнение упражнения

В спортивном протоколе нет поля `verified`, подтвержденного сервером. Клиентская камера вызывает отправку `rep`/`raidHit`; сервер видит только сообщения и время. `rooms.rep` проверяет фазу/интервал; `clans.raidHit` проверяет владельца attackId, время, темп, максимальный урон; `guard.clanReps` ограничивает присланное число. Сохранения содержат клиентские `days/manual/log`; `SaveStore.put` не проверяет их по журналу подтвержденных упражнений. `cameraDays` и `challengeScore` вычитают клиентский признак ручного ввода. Авторизованный измененный клиент может имитировать правдоподобный темп и не пометить ввод ручным. Камера и подпись Telegram удостоверяют разные вещи: камера работает на устройстве, подпись удостоверяет аккаунт.

Поле `verified` найдено в `shared/villagePvp.ts` и ответах `server/villages.ts`; оно относится к серверному расчету деревенского боя, не к физическому упражнению. Его нельзя использовать как доказательство camera verification.

Локальная проверка границы: вызвать `Room.rep` в фазе fight без MediaPipe/камеры с допустимыми интервалами; существующие unit-тесты Rooms именно так моделируют удары. Создать SaveStore(null) с days/log и manual=0; cameraDays/challengeScore включают эти данные в счет в пределах лимитов. Не проводить такую проверку на production. Серверный журнал попыток с nonce, сроком и защитой от replay улучшит целостность, но сам по себе не докажет движение тела. Изменение рейтингов требует отдельного согласования совместимости.

### P2: запись JSON и выдача ответа не атомарны

`Guard.save` и `SaveStore.save` откладывают flush на 2 секунды, кланы — на 1 секунду. Жесткое завершение процесса до flush теряет изменения, независимо от успешного ответа. Отдельные файлы не образуют транзакцию с клиентским прогрессом. Для проверки использовать исключительно временную директорию, получить награду/сохранить прогресс, принудительно завершить отдельный тестовый subprocess до flush и заново прочитать хранилища. Нужны интеграционные crash/restart-тесты; существующие memory tests не покрывают эту гарантию.

## Этап 4: аналитика

Положительное: собственный сервер; client SHA-256 и server HMAC для идентификаторов; raw видео/позы не передаются; дневные агрегаты вместо сырого event log; TTL 45 дней для дней и 120 дней для пользователей; лимиты payload/IP/числа ключей; админские права перепроверяются. D1/D7 считаются по точным дням активности, будущие дни дают null.

Пробелы: список событий старый, события имеют только n/p; нет sessionId/eventId/per-event timestamp, длительности камеры, positioning/countdown/tracking/abandonment, разреза воронки по версии/платформе. Версия/платформа сохраняются только в примере ошибки. Повтор пакета увеличивает счетчики. Клиент держит до 100 событий, сервер читает только первые 50; остаток пакета может быть потерян. Отправка best-effort без восстановления после сети. Текущая воронка — независимые биты по пользователю за период, не упорядоченные шаги одной сессии, поэтому ее нельзя выдавать за строгую последовательную конверсию. `statsPage.worstStep` сравнивает соседние независимые счетчики. В отображении процентов не везде явно показан знаменатель.

Проверить новыми тестовыми сессиями: дубли eventId/пакета, события вне порядка, возвращающийся старый пользователь, камера denied→retry→granted, несколько тренировок/сессий, переход суток, незрелая D7-когорта, unknown version/platform, отсутствие локального storage, offline flush. Сырые координаты и изображения для этих метрик не нужны.

## Независимый review промежуточного diff

Проверены реальные изменения `trainingLifecycle.ts`, `useRepCamera.ts`, `StartGate.tsx`, `MissionPlay.tsx`, `WorkoutSession.tsx`, `repCounter.ts`. Это замечания к промежуточному состоянию; после исправлений их нужно перепроверить.

1. Feature flag `VITE_POSITIONING_GATE=0` не отключал `StartGate.disabled={!!hint}`. Поэтому возвращение прежнего свободного запуска не гарантировалось. Передано разработчику: явный признак блокировки кнопки, связанный с флагом.
2. `probe = counterFor(exercise)` создавался только при start; switchExercise менял только основной счетчик. Состояние трекинга после смены упражнения проверялось по первому упражнению. Передано разработчику: синхронизировать readiness probe со сменой упражнения.
3. Успешное завершение через onFrame false вызывало stop→CANCELLED. COMPLETED существовал в типе, но не использовался на пути завершения. Нужен явный completion contract до событий аналитики.
4. При runtime ошибке распознавания hook прекращал loop и ставил ERROR, но экраны не переводили phase/status в существующий экран ошибки. Требуется recovery-путь с повтором/выходом и сохранением правил списания жизни.
5. Допуск между кадрами 250 ms навсегда блокировал readiness при устойчивых кадрах раз в 300 ms. Воспроизведено локально: `TrainingLifecycle.cameraReady(true)`, вызовы frame(true, now) от 0 до 9000 с шагом 300, результат POSITIONING. Нужен настраиваемый предел, ограничение минимальной скорости либо явно задокументированная совместимость, не обход проверки стабильности.

Положительное в diff: поколение асинхронного запуска останавливает запоздавшие streams; stream tracks и srcObject освобождаются; timer onFrame отложен до readiness/countdown; ACTIVE/TRACKING_LOST не возвращается к подготовке, поэтому потеря трекинга сама по себе не продлевает активную попытку. Для claim receipts и серверной границы доверия изменений поведения не внесено.

## Этап 6: воспроизводимые тесты доставки наград

Добавлен `server/claimDelivery.test.ts` (6 тестов). Команда `npm test -- server/claimDelivery.test.ts server/fairplay.test.ts server/clans.test.ts src/game/progress.test.ts`: **4 файла / 44 теста PASS**. Первый запуск обнаружил неверное использование not.toContain на optional поле undefined в новом тесте; matcher исправлен на проверку пустого массива, повторный запуск успешен.

Новые тесты подтверждают фактическое ограничение, а не устранение дефекта:

- При потерянном ответе claimRaid/claimWar клиент не получает монеты, повторный запрос отклоняется.
- После flush обоих временных файлов и создания новых Guard/ClanStore отказ сохраняется. Тест работает только с автоматически созданной временной директорией.
- Другой игрок не получает чужую награду, legacy claimed без receipt не перевыплачивается.
- Клиентские `claimRaid` и `claimWar` дедуплицируют текущий payload, но помнят только 21 последний ключ; после вытеснения старого ключа повторное применение его payload снова увеличивает монеты. Это проверка предела клиентского контракта, не утверждение, что текущий сервер уже выдает старые receipts.

Безусловный server-only replay cache не внедрен: ограниченный клиентский dedupe нельзя считать бессрочным серверным подтверждением выплаты. Дополнительно существующий UI скрывает кнопку по server claimed, поэтому один кэш ответов не создает путь восстановления после reconnect. Безопасное исправление должно определить срок/ключ запроса, совместимость старых клиентов и legacy claims, авторитетное применение к account progress, восстановление после обрыва и acknowledgement. Потребуются тесты повторов, нескольких устройств, смены клана/аккаунта, rollover недели, старых сохранений и аварийного перезапуска. Баланс, клиент Progress и server guard/clans не менялись. Статус этапа 6 остается **FAIL: подтвержденный дефект доставки**.
