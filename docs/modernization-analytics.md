# Ограниченное расширение аналитики камеры — 2026-11-05

Статус этапа 4: **FAIL / частично реализован: локальная работа не закончена**. Это безопасная основа инструментирования, не готовая административная воронка.

## Реализовано

- Единый allowlist `shared/trainingTelemetry.ts`: camera_permission_requested/granted/denied, camera_ready, positioning_started/completed, countdown_started, exercise_started/completed/abandoned, tracking_lost, recognition_error, first_rep_detected.
- Каждое новое и существующее клиентское событие получает непрозрачный идентификатор текущей сессии приложения, последовательный eventId, timestamp и версию сборки. Сессионный токен создается заново при запуске JS; он не связан с аккаунтом и не сохраняется в localStorage.
- `createTrainingTelemetry()` возвращает reporter одной попытки. Milestones дедуплицируются на попытку; tracking_lost и recognition_error допускают разные эпизоды, поэтому вызывающая сторона должна сообщать переходы, а не каждый кадр.
- Схема metadata пропускает только упражнение, ограниченное время камеры (до 600000 мс), число неудачных попыток (до 1000), enum этапа выхода и enum причины. Произвольные строки, координаты, изображения, видеопоток и неизвестные свойства отбрасываются перед очередью и повторно на сервере.
- Сервер принимает новые события только с валидным envelope. Старые события и сохраненные агрегаты остаются совместимыми. Новые события увеличивают дневные счетчики, сумма/число camera_ready дают среднее время камеры; positioning_completed хранит сумму неудач и число образцов; причины ошибок и этапы выхода — отдельные ограниченные счетчики.
- Клиент передает не более 50 событий за пакет; остаток остается в очереди для следующей отправки. Исправлена конкретная потеря событий 51–100 при прежнем server slice(0,50).
- Повтор одного нового события (anon+sid+id) не учитывается повторно в течение часа в пределах bounded cache из 5000 ключей. В cache только HMAC-ключ, raw sessionId и metadata на диск не записываются. Дневные агрегаты хранятся по существующей политике 45 дней, анонимные пользовательские когорты — 120 дней.

## Ограничения и следующие действия

- Reporter подключен в useRepCamera только для managed первого подхода кампании/программы (prepare:true). Прочие режимы не отправляют новую воронку, чтобы не создавать completed без started. Legacy telemetry сохранена.
- Не добавлены прочие события пути пользователя, новый dashboard, разрезы по платформам/версиям, session-level воронка с числителями и знаменателями, новая D1/D7 когорта. Существующие legacy funnel/retention не переименованы в новые метрики.
- Клиентская очередь ограничена 100 событиями. При переполнении старые теряются. Нет durable queue, повторов failed fetch, гарантии beacon-доставки или exactly-once после перезапуска сервера/истечения replay cache. Это аналитика best effort, не журнал начисления наград.
- Время приема остается серверным днем агрегата; at проверяется в окне -24 часа/+5 минут и не используется как доверенное серверное время. Сильно неверные часы устройства приводят к отклонению новых событий.
- Полная длительность позиционирования и точное определение неудачной попытки требуют согласованного инструментирования вызывающей стороны. Нельзя оценивать точность CV по счетчику ошибок без реальной разметки.
- Ручная локальная проверка: открыть тестовую игру, разрешить/отклонить камеру, выполнить start/cancel/retry и tracking loss; сравнить Network /api/telemetry с ожидаемыми переходами. Не отправлять настоящие записи или ориентиры тела. Затем проверить агрегаты через тестовый экземпляр Telemetry. Production не использовался.

Откат: вернуть перечисленные telemetry файлы коммитом revert. Новые поля wire payload обратно совместимы; обратимых/необратимых миграций данных не требуется. Новые счетчики останутся неиспользуемыми старым клиентом, существующие данные не удаляются.
